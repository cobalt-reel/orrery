# Layouts: a library, cycling and a picker (design, plan and as built)

A selection of layouts, in three parts: a library of layouts tuned for real
screens, a way to step through them, and a picker that shows them. Until now the example config had two layouts
(`wall`, `halves`) on two binds, and nothing on screen said which one was in use.

## Design

- **`cycle-layout next|prev`**, a bind action and a request (`orrery msg cycle-layout next [MONITOR]`, JSON
  `{"cmd":"cycle-layout","cycle":"next","monitor":...}`). Pure, like `layout`: the target monitor is the named one or
  the focused one (the same resolution, now one helper); the next layout is the one after the workspace's current
  layout in config order, wrapping round. A workspace whose layout is no longer in the config (kept across a reload)
  goes to the first (`next`) or last (`prev`). One layout: it is laid out again, which changes nothing.
- **`layouts` in `state`**: the config's layouts in config order, as `Layout` serializes (name, grid, weights when
  set, slot specs). `Layout`/`SlotSpec` gain `Deserialize` only because `StateView` crosses links; the config remains
  the only place layouts are validated. Not in the event stream: the picker reads `state` once when it opens, and the
  bar only needs the names, which `layout` events already carry.
- **Default binds** `Mod+bracketright` / `Mod+bracketleft` (free in the example config).
- **`examples/layouts.kdl`**: eight layouts as an includable snippet (`single`, `tall`, `wide`, `centre`, `columns`,
  `quad`, `six`, `sidebar`), names chosen not to clash with the example's. Slot 0 is the main slot wherever a layout
  has one, because a switch fills the new layout's slots in order: the work in slot 0 stays the main thing.
- **Bar**: this screen's layout name before the clock, in the badge colour, from `state` and `layout` events; dropped
  first when the bar is too narrow.
- **Picker** `examples/kitty/layouts.py` (standard library, fzf, a `kitten panel` like the launcher): lists the
  layouts with their slot count and which is in use, starts on that one, and previews each as box-drawing art fitted
  to the focused screen's proportions (cells counted twice as tall as wide), grid lines weighted as orrery weights
  them, slots numbered from 1 and named. The preview gets the layout as a hidden fzf field, so it never asks orrery
  again. Enter sends `layout NAME SCREEN` for the screen focused at opening (the panel itself never moves it).
  Bound to `Mod+backslash` in the kitty snippet.

## Plan and tests

1. `Action::CycleLayout`, `Request::CycleLayout` (+ wire twin, words, verb): unit tests for parsing, refusals, the
   bind lookup and action mapping; `apply` tests: config order and wrap both ways, the other screen untouched, a named
   monitor, equivalence with `layout NAME`, a vanished layout, errors changing nothing.
2. `StateView::layouts` (round-trip test includes one); `tests/control.rs` end to end: `state` lists them,
   `cycle-layout` by words and JSON, an unknown monitor refused.
3. The library, checked with `orrery check` together with the example config and the kitty snippet.
4. Bar: model and rendering tests. Picker: `test_layouts.py` (grid lines and weights, shared borders, labels, fitting,
   listing).
5. README: default keys, `orrery msg`, `state`, the action table, "A library of layouts", the kitty desktop, and a
   "Layouts: checklist" for the live test.

## As built

As planned. `cargo test`, `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and the kitty scripts'
unit tests pass; `cycle-layout` and the picker's listing and previews were also run against a headless orrery.
